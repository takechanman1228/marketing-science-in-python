5.2 产品品类组合优化

关于中文版

品类评审已经排上日程：货架陈列团队想要回一些货架空间，品类经理必须点名要放弃哪些 SKU。一个表现不佳的产品不只是占地方：它占用库存、让供应链更复杂，还让货架更难逛。要决定的是砍掉哪些产品、保留哪些，以及如何在全连锁推广之前验证这些判断。

本章在两年的杂货交易数据上完整走一遍这个决策：按收入筛选长尾，检查需求是否会留在店内，然后交回一份按每个 SKU 测试安全程度排序的候选短名单。

配套 Notebook： sec5.2_assortment_optimization.ipynb 在 Dunnhumby Complete Journey 杂货数据集上复现了收入 ABC 筛选、替代检查和行动分配。

注记为什么用收入而不是利润？

本章分析的是收入，因为公开的 Dunnhumby Complete Journey 数据集不包含产品成本或 COGS。当生产团队拥有成本数据时，同样的流程可以在毛利或边际贡献上运行；只有业务解读会变，从收入风险管理变为利润优化。

为什么砍 SKU 这么难

品类组合（assortment）的膨胀有其正当理由：采购想要广泛的覆盖，品牌也在不断推出变体。更精简的货架也可能更好逛，不过关于这个效应有多大，选择过载的文献结论不一（见延伸阅读）。不对称之处在组织层面：多一个 SKU 的成本是弥散的、容易被忽视的，而下架一个产品则是显眼的、有时不受欢迎的举动。品类组合优化归根结底是一个决策过程。数据的作用是给团队一个站得住脚的行动理由。

品类组合优化的工作流程

这个流程依次回答两个问题：

  1. 筛选 → 候选池。 哪些产品贡献的收入很少、处在长尾？
  2. 替代检查 → 安全性评估。 对每个候选，如果我们把它下架，需求会留在我们店里吗？

在表现更好的产品中有合理替代品的候选，是风险较低的测试候选。没有替代品的，先测试再行动。在匹配门店测试验证之前，没有什么是确认安全的。

第 1 步：按收入筛选 SKU

在决定下架什么之前，我们需要把 SKU 的范围缩小。一家杂货店可能经营数千种产品，但一小部分驱动了大部分收入，而长尾商品每一种带来的收入都很少。下架候选就来自那条长尾。

零售团队常用一种帕累托式的排名，叫作 ABC 分析。产品按贡献排序，通常是销售额或利润，有时也按销量，然后分成三档。

  • A 类商品（前约 20%）：关键少数。它们驱动了所选指标的大约 80%。保护、监控并优化它们。
  • B 类商品（接下来约 30%）：重要的中间层。稳定的贡献者，需要的关注较少。
  • C 类商品（末尾约 50%）：长尾。单个很小，合起来很嘈杂。是精简的候选。

C 类产品是你开始构建候选池的地方。不是每个 C 类商品都应该下架，但任何你考虑砍掉的产品都应该来自这个组。

在代码中，按累计收入份额给 SKU 排名，切分成 A/B/C 三档，并把 C 类长尾作为候选池：

ranked = sku_summary.sort_values("revenue", ascending=False)["revenue"]
# Classify on the cumulative share *before* each SKU, so the SKU that crosses
# the 80% line still counts toward A (and a single dominant SKU stays A).
cum_before = (ranked.cumsum() / ranked.sum()).shift(fill_value=0)
sku_summary["abc_revenue"] = pd.cut(cum_before, bins=[0, 0.80, 0.95, 1.0],
                                    labels=["A", "B", "C"], right=False)

# Candidate pool = C-rank by revenue (the long tail)
candidates = sku_summary[sku_summary["abc_revenue"] == "C"]

完整的函数，包括零销售/负销售过滤和对 NaN 安全的分箱，在配套 Notebook 中。

图 1 展示了约 39,000 个 Dunnhumby 杂货 SKU（剔除 38 个无销售的之后）的收入帕累托曲线。收入高度集中：不到 20% 的 SKU 产生了 80% 的销售额，而 C 类池（abc_revenue == "C"）包含 63% 的 SKU，却只有 5% 的收入。这条长尾构成了候选池。单凭数量，它值得被检视，而不是被捍卫。

C 类收入让一个产品进入候选池，但离下架还差一步。第 2 步判断哪些候选可以安全测试，哪些需要更多谨慎。

第 2 步：替代检查，“需求会留下来吗？”

对每个 C 类候选，问题是：如果我们把它下架，顾客会从我们这里买别的东西，还是离开这家店？

在同一个子品类内，很少出现在同一个购物篮里的产品可能是替代品。购物者通常买一个品牌的酸奶，而不是三个。我们用购物篮共现度低（以提升度衡量）作为替代的代理指标：

\[\text{Lift}(A, B) = \frac{P(A \cap B)}{P(A) \times P(B)}\]

提升度 > 1 意味着两个产品倾向于被一起购买（互补品）；提升度 < 1 意味着它们很少一起被购买，在同一子品类内这暗示它们互为替代；提升度 = 0（从未出现在同一个购物篮）是最强的信号。同子品类的约束很重要：跨品类的低共现只说明产品满足不同的需求（麦片与意面），并不说明它们互为替代。

这是代理指标，不是证据。低共现也可能反映不同的购物场合或客户细分群体。

对每个 C 类候选，这项检查扫描它的同子品类同伴（限定为收入 A/B 类、体量足以吸收转移需求的 SKU），并标记其中提升度低的那些：

co_occur = len(cand_baskets & peer_baskets)
if co_occur == 0:                       # never bought together → strongest signal
    subs.append({"substitute": peer_id, "lift": 0.0})
else:
    lift = (co_occur / total_baskets) / (p_cand * p_peer)
    if lift < lift_threshold:           # low Lift within a sub-category → likely substitute
        subs.append({"substitute": peer_id, "lift": round(lift, 3)})

完整的函数，包括子品类分组、收入 A/B 类替代品池和最小购物篮数保护，在配套 Notebook 中。

还有两个可选的加强手段。交叉价格弹性为正时（如果有的话），支持替代关系。当购物篮数据稀疏时，比如新品或小门店，属性相似度（如品牌、价格档次或使用场景）可以是一个实用的备选方案。

输出：一份打分后的候选清单

长尾太大，无法整体打分，所以 Notebook 对 150 个 C 类 SKU 打分：购买最频繁的 100 个，加上同一子品类中的其他 C 类 SKU，全部在两年内至少出现在 30 个购物篮中。一个只被买过十来次的 SKU，无论哪个方向都承载不了替代信号。然后第 1 步和第 2 步分配三种行动之一。表 1 展示了每种行动各一个真实候选（子品类标签已整理以便阅读）：

在这 150 个中，行动的分布是 105 / 28 / 17。被检视的长尾大多数都有品类内替代品，也没有特殊的购物篮角色，对它们来说零共现（提升度为 0.0，交易数据中最强的替代信号）是常见情形。这不是一份下架清单。这是一份短名单，按每个候选优先测试的安全程度排序。

有明确品类内替代品的候选，是最安全的下架测试对象。没有明确替代品的 17 个则是相反的情形：能吸收其需求的收入 A/B 类同伴不到五个，所以需求可能离开这家店。暂时保留该产品，寻找降低其成本的方法，比如更小的包装或更好的供应商条件，或者在下架前谨慎测试。

中间的 28 个是针对光环效应的一道防线。一个经常与更高价值商品一起出现的低价 SKU，可能有助于吸引那些购物篮，所以下架它可能减少其他地方的销售。对这些情形要先调查再砍，而不是只依赖收入。在密集的杂货数据中，几乎每个 SKU 都会与某些东西共现，所以只对最清晰的情形使用这个标记。另外，不是每个低收入 SKU 都应该进入候选池。有些产品靠带动到店、锚定价格形象或彰显品类可信度来赢得货架位置，这些角色是收入和提升度都捕捉不到的。

推广之前先验证

打分后的清单是一组假设，不是一份下架清单。在推开一次删除之前，先做一个小规模的匹配门店测试：在实验门店下架该 SKU，保持可比的对照门店不变，并监控子品类收入、每篮收入和购物篮数。

不要评估被下架 SKU 自己的销售；按定义它们会是零。问题是需求是否留在了品类里、留在了购物篮里。如果结果不确定，就不要推广这次下架。

要点

  • 收入 ABC 产生的是候选，不是决策。同子品类低共现是替代的代理指标，不是证据，而一个锚定了高价值购物篮的便宜 SKU 可能值得保留。
  • 没有匹配门店测试绝不推广。衡量子品类收入、每篮收入和购物篮数，而不是被下架 SKU 自己的销售。结果不确定不等于绿灯。
